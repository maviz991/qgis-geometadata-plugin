> Bug 38 (RESOLVIDO, aguardando confirmação em uso real): usuário reproduziu de novo - múltiplos cliques rápidos no logo CDHU do header (navega pra Home) deixava o badge de status "Verificando..." preso indefinidamente e derrubava o QGIS.
> Causa: `navigate(panelId)` (`app.js`) não tinha NENHUMA guarda contra chamadas repetidas - cada clique disparava `bridge.navigate(panelId)` de novo, encadeando `nav_changed` → `loadPanel` → `bridge.load_panel_html` → `onPanelLoaded('home')` → `check_services_status()`, sem esperar o ciclo anterior terminar. N cliques rápidos empilhavam N navegações completas e 2N `_ServiceStatusWorker` (QThread) concorrentes batendo nas mesmas URLs, além de trocar `container.innerHTML` várias vezes por segundo na `QWebEngineView` - respostas atrasadas de checagens antigas se pisando explicam o "Verificando..." preso (uma resposta velha reescrevendo por cima de uma mais nova ainda em voo), e o volume de QThreads/reflow simultâneo é a mesma classe de estresse nativo por trás dos Bugs 33-35 (não uma reentrância isolada de UM worker, mas um acúmulo descontrolado de vários). `check_services_status()` (`ui/main_bridge.py`) também não tinha guarda nenhuma contra sobreposição - cada `onPanelLoaded('home')` disparava um novo par de workers incondicionalmente, mesmo com o par anterior ainda rodando.
> Fix: `navigate()` (`app.js`) ganhou a flag `_navInFlight` - ignora chamadas novas enquanto uma navegação já está em andamento, limpa em `onPanelLoaded()` (que sempre roda ao final de qualquer navegação, garantido porque `load_panel_html` nunca propaga exceção - sempre retorna uma string, mesmo em erro). `check_services_status()` ganhou guarda complementar (`if self._status_workers: return`) contra sobreposição, defesa adicional caso outro caminho (não só o clique no logo) dispare a checagem de novo antes da anterior terminar. `?v=` de `app.js` bumped em `main.html` (19→20).
> Melhoria acoplada (pedido do usuário, elimina a causa raiz de vez): `check_services_status()` checava GN/GS de novo TODA vez que a Home carregava (inclusive após login, e cada ida-e-volta a outro painel e volta) - desnecessário, já que esse status muda pouco. Novo `self._service_status_cache` (`MainBridge`) guarda o resultado da primeira checagem da sessão do plugin; chamadas seguintes reemitem o cache direto (síncrono, sem QThread nenhuma) em vez de bater na rede de novo. "Abriu o plugin, verificou uma vez, guardou" - nem revisitar a Home nem logar disparam uma nova checagem; só fechar e reabrir o plugin (nova instância de `MainBridge`) zera o cache.

> Bug 39 (RESOLVIDO): Badge "Atualização disponível" imediatamente após "Baixar Metadado" do servidor, mesmo sem nenhuma camada QGIS ativa.
> Causa: `pullGnRecord` (`geonetwork.js`) chamava `checkGnSync` depois de popular o formulário com os dados do GN. Isso disparava `_GnSyncCheckWorker` (`geonetwork_workers.py`), que compara o conteúdo remoto (`remote_title`/`remote_abstract`/`remote_keywords`) contra o que está *salvo localmente* (`local_snapshot`). Sem camada QGIS ativa (ou sem nenhum save anterior), `local_snapshot = {}`, então `local_title = ''`, `local_abstract = ''`, `local_keywords = []` — sempre divergem do conteúdo real do servidor → `diverges = True` → `sys_update_available` falso-positivo. A lógica de comparação está correta para o seu propósito (detectar atualização remota após uma edição local), mas não faz sentido nesse contexto de pull: o formulário acabou de ser preenchido com EXATAMENTE o que está no servidor.
> Fix: `pullGnRecord` (`geonetwork.js`) passou a setar `setGnBadge('sys_synced')` diretamente após o pull, sem chamar `checkGnSync` — mesmo padrão já usado por `gn_publish_succeeded`. Pull exige login → nível sistema (`sys_*`) é correto. `_gnSyncUuid` e `_gnSyncUuidLayerName` ainda são atualizados para que o botão "↻ Atualizar" manual funcione a partir daí.

> Bug 40 (RESOLVIDO): Badge "Atualização disponível" ao reabrir o plugin após ter feito um pull do servidor (sem camada QGIS ativa), mesmo sem nenhuma alteração feita.
> Causa: o Bug 39 corrigiu o badge imediato após o pull (setar `sys_synced` direto em vez de chamar `checkGnSync`), mas ao fechar e reabrir o plugin a sessão JS é zerada. O formulário é recarregado do draft (salvo por `_saveDraftNow()`) e `checkGnSync` é disparado de novo — dessa vez sem o estado em memória que havia sido setado. `check_gn_sync` (Python) carrega `saved = ps.load(layer)`, que é `{}` quando não há camada ativa ou nenhum save anterior no banco/sidecar. `_GnSyncCheckWorker` compara remoto vs `{}`: sempre diverge → `sys_update_available` falso-positivo de novo.
> Causa raiz: o badge "Sincronizado" setado na sessão anterior existia apenas em memória JS — não havia nenhum estado persistido que sobrevivesse ao fechar/reabrir.
> Fix: nova camada de persistência **pull baseline** (`geometadata_pull_baselines.json`, mesmo diretório de `geometadata_form_draft.json`). Formato: `{layer_key: {uuid, snapshot}}` onde `snapshot = {title, abstract, MD_Keywords}` — exatamente os campos que `_GnSyncCheckWorker` compara. (1) `pullGnRecord` (`geonetwork.js`) chama o novo slot `gnBridge.save_pull_baseline(uuid, snapshotJson)` imediatamente após o pull bem-sucedido. (2) `save_pull_baseline` (`GeoNetworkBridge`, `geonetwork_bridge.py`) salva o baseline no arquivo, keyed por `_layer_key()`. (3) `check_gn_sync` (Python), após tentar carregar `saved` do banco/sidecar, aplica o fallback: se `saved` ainda for vazio, lê o arquivo de baselines e, se existir uma entrada cujo `uuid` bate com o que foi pedido, usa o `snapshot` como `local_snapshot` do worker. Resultado: worker compara remoto vs baseline do pull → `diverges = False` → `sys_synced`. (4) `clear_draft` agora também apaga o baseline da camada ativa (reset completo). O baseline é ignorado automaticamente quando `ps.load(layer)` devolver algo (save local passa a ser a fonte de verdade mais confiável).
