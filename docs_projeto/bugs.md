> Bug 51 (RESOLVIDO, aguardando confirmação em uso real): usuário reportou o QGIS fechando ao usar o "Plugin Reloader" (ferramenta do próprio QGIS pra recarregar o código do plugin sem reiniciar) enquanto o GeoMetadata estava em uso.
> Causa: `GeoMetadataDialog.closeEvent` (e os equivalentes em `login_dialog.py`/`gateway_login_dialog.py`) usam o padrão `w.quit(); w.wait(2000)` pra parar qualquer QThread ainda em voo antes do diálogo ser destruído (mesma causa raiz das crashes dos Bugs 33-35/44 - destruir uma QThread ainda `isRunning()` faz o Qt chamar `std::terminate()`, fechando o QGIS inteiro sem crash dump). O problema: `quit()` só sinaliza encerramento pro event loop PRÓPRIO da thread (`QThread.exec_()`) - NENHUM worker deste plugin roda um; todos são só um `run()` síncrono fazendo uma chamada de rede bloqueante (`requests`/`urllib`), então `quit()` não interrompe nada de verdade - quem faz o trabalho é só o `wait(2000)`, que dá no MÁXIMO 2 segundos pro worker terminar sozinho antes de desistir e deixar o diálogo ser destruído mesmo assim. 2s é pouco: várias chamadas usam timeout de até 15-60s (ex.: `_GsSearchLayersWorker`, WMS GetCapabilities documentado como lento nesse servidor - Bug 47), e mesmo uma chamada bem-sucedida "normal" pode facilmente passar de 2s sob carga.
> Por que isso nunca foi percebido num fechamento normal do QGIS (X da janela): o comentário original já assumia isso - "o processo Qt já vai encerrar de qualquer forma" - um `std::terminate()` nesse cenário é irrelevante pra experiência (o processo inteiro ia fechar mesmo). "Plugin Reloader" quebra essa suposição: ele NÃO fecha o QGIS, só descarrega/reimporta o módulo do plugin dentro do MESMO processo ainda rodando - um worker que sobrevive ao `wait(2000)` e segue rodando quando o reload continua causa um `std::terminate()` que dessa vez derruba um QGIS que, de outra forma, continuaria de pé.
> Fix: `wait(2000)` → `wait(10000)` em todos os pontos de limpeza (`GeoMetadata_dialog.py` closeEvent - 10 ocorrências -, `login_dialog.py`, `gateway_login_dialog.py`) - cobre a esmagadora maioria dos casos reais (a maior parte das chamadas termina bem antes disso). Ressalva honesta (não eliminada por completo, documentada nos comentários): ainda existe uma janela residual pra um worker GENUINAMENTE preso além de 10s - não há uma forma segura de cancelar uma `requests.get()`/`urlopen()` já em voo sem fechar o socket manualmente (fora do escopo desse fix), então esse caso extremo (raro) ainda pode reproduzir o crash.
